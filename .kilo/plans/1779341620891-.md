# PiNyx Gateway Layer — Implementation Plan

## Overview

PiNyx is a local model gateway that sits between Pi (coding-agent) and AI providers. Pi sends LLM requests to PiNyx instead of directly to providers. PiNyx classifies intent, applies rules/budget, selects the optimal model, and proxies the request.

**Stack:** Rust core (Axum) for routing/proxy logic + Bun/TypeScript for dashboard/UI.

**Config:** JSON (`pinyx.json`)

---

## User Experience Flow

```
1. Start PiNyx:     pinyx                    # reads pinyx.json, starts on localhost:7331
2. In Pi:           /login                   # PiNyx appears in provider list (via extension)
                   → select "PiNyx (local)"  # extension verifies PiNyx is running
                   → connected ✓              # all models from PiNyx are now available
3. Use Pi normally:  requests go through PiNyx → real providers
```

**Key:** API keys for all cloud providers (Anthropic, OpenAI, DeepSeek, etc.) live in PiNyx's `pinyx.json`. Pi never sees real keys. The Pi extension registers PiNyx as a provider with a lightweight OAuth "login" that just confirms the gateway is running.

## Integration Strategy: Pi Extension + Local Proxy

### How Pi connects to PiNyx

The Pi extension (`~/.pi/agent/extensions/pinyx/index.ts`) does three things:

1. **Registers PiNyx as a provider** with OAuth support so it appears in `/login`
2. **Fetches available models** from PiNyx's model registry on startup
3. **Routes all requests** through `http://localhost:7331`

```typescript
export default async function (pi: ExtensionAPI) {
  pi.registerProvider("pinyx", {
    name: "PiNyx (local)",
    baseUrl: "http://localhost:7331/v1",
    api: "openai-completions",
    models: [], // populated below

    oauth: {
      name: "PiNyx (local)",
      async login(callbacks) {
        const res = await fetch("http://localhost:7331/health");
        if (!res.ok) throw new Error("PiNyx is not running. Start it with: pinyx");
        callbacks.onAuth({ url: "http://localhost:7331" });
        return {
          refresh: "pinyx-local",
          access: "pinyx-local",
          expires: Date.now() + 365 * 24 * 60 * 60 * 1000,
        };
      },
      async refreshToken(creds) {
        return creds;
      },
      getApiKey(creds) {
        return creds.access;
      },
    },
  });

  const res = await fetch("http://localhost:7331/v1/models");
  if (res.ok) {
    const { data } = await res.json();
    // Re-register with discovered models
    pi.registerProvider("pinyx", {
      baseUrl: "http://localhost:7331/v1",
      api: "openai-completions",
      models: data.map(m => ({
        id: m.id,
        name: m.name,
        reasoning: m.reasoning,
        input: m.input,
        cost: m.cost,
        contextWindow: m.contextWindow,
        maxTokens: m.maxTokens,
      })),
    });
  }
}
```

### Why this approach

- `/login` in Pi → select PiNyx → done. No env vars, no `models.json` editing.
- API keys live only in `pinyx.json`. Pi never touches real provider credentials.
- No auth between Pi ↔ PiNyx (localhost only, `127.0.0.1` binding).
- PiNyx supports dual APIs (OpenAI + Anthropic) so any Pi-compatible provider works behind it.
- Dynamic model discovery: PiNyx tells Pi what's available.

## Phased Implementation

### Phase 1: Core Proxy + Pi Extension (MVP)

**Goal:** PiNyx runs locally, Pi connects via `/login` → "PiNyx (local)", requests are transparently proxied to providers with logging. No classification yet.

**Tasks:**

1. **Rust project scaffold**
   - `cargo init` with Axum, Tokio, Reqwest, serde_json, tracing
   - Binary crate: `pinyx`
   - Config: `pinyx.json` in `~/.pinyx/` or `./pinyx.json`

2. **Configuration system**
   - Load `pinyx.json` from `~/.pinyx/pinyx.json` (global) or `./pinyx.json` (project)
   - Validate provider configs (api type, baseUrl, apiKey)
   - Resolve apiKey values as env var names → literal values
   - Hot-reload config on SIGHUP

3. **OpenAI-compatible endpoint (`POST /v1/chat/completions`)**
   - Accept OpenAI Chat Completions format
   - Extract model from request body (format: `provider/model-id`)
   - Route to configured provider adapter
   - Stream responses back (SSE `data:` lines)
   - Pass through all OpenAI params (temperature, tools, tool_choice, etc.)

4. **Anthropic-compatible endpoint (`POST /anthropic/v1/messages`)**
   - Accept Anthropic Messages API format
   - Proxy to Anthropic (or Anthropic-compatible provider)
   - Stream responses back (SSE with `event: content_block_delta` etc.)

5. **Provider adapters**
   - `AnthropicAdapter` — forwards to Anthropic Messages API, handles SSE streaming
   - `OpenAIAdapter` — forwards to OpenAI Chat Completions API, handles SSE streaming
   - `GoogleAdapter` — forwards to Google Generative AI API
   - Each adapter: request forwarding, streaming passthrough, error mapping

6. **Request/response logging**
   - JSONL log of every request to `~/.pinyx/logs/`
   - Fields: timestamp, provider, model, input_tokens, output_tokens, cost, latency, status

7. **Model registry endpoint (`GET /v1/models`)**
   - Returns all available models across configured providers
   - OpenAI-compatible format: `{ object: "list", data: [...] }`
   - Includes metadata: cost tiers, capabilities, context windows, reasoning support
   - Used by Pi extension for dynamic discovery

8. **Health/status endpoint (`GET /health`)**
   - Returns: `{ status: "ok", providers: { anthropic: "configured", openai: "configured" } }`
   - Used by Pi extension OAuth flow to verify PiNyx is running

9. **Pi extension (`extensions/pi-pinyx/`)**
   - Register PiNyx as provider with OAuth support
   - OAuth `login()` calls `GET /health` to verify gateway is running
   - Fetch model list from `GET /v1/models` on startup
   - Register models with Pi via `pi.registerProvider()`
   - Add `/pinyx-status` command showing gateway health, connected providers, current model

**Deliverable:** User runs `pinyx`, then in Pi does `/login` → "PiNyx (local)" → connected. All Pi requests flow through PiNyx with full logging. No classification or routing yet — pass-through proxy.

### Phase 2: Intent Classification + Rule Engine

**Goal:** PiNyx classifies request intent and selects optimal model based on rules.

**Tasks:**

1. **Heuristic intent classifier**
   - Keyword/pattern-based classification (no model needed)
   - Analyze: request messages, system prompt content, tool calls in context
   - Classification labels: `user_chat`, `planning`, `architecture`, `coding`, `debugging`, `refactor`, `summarization`, `validation`, `research`, `tool_request`, `risky_action`, `long_context`
   - Input: last N messages from request payload
   - Output: intent label + confidence score
   - Example heuristics:
     - Messages with `read`, `write`, `edit`, `bash` tool results → `coding`
     - Long system prompt with architecture discussion → `architecture`
     - Short user message without tool context → `user_chat`
     - Messages containing "debug", "error", "fix", "traceback" → `debugging`

2. **Rule engine**
   - Evaluate declarative rules from `pinyx.json` in order
   - First matching rule wins
   - Default fallback: use the model from the original request
   - Simple expression evaluator: `source == 'user'`, `intent == 'coding'`, `context_tokens > 100000`

3. **Model tier system**
   - Tiers defined in `pinyx.json`: `good`, `mid`, `cheap`
   - Selection strategies: `round_robin`, `cheapest`, `fastest`, `random`
   - Rules map to tier preferences: `prefer_good_model` → `good` tier, etc.

4. **Request enrichment pipeline**
   - Middleware that attaches metadata to each incoming request
   - Metadata: source (user/internal), intent, context_size, previous_failures
   - Pipeline: classify → evaluate rules → select tier → select model → override request model

5. **Classification debug endpoint (`POST /classify`)**
   - Send a request payload, get back: intent, confidence, selected tier, selected model, matched rules
   - Useful for tuning rules without running Pi

**Deliverable:** PiNyx automatically routes coding tasks to cheap models and user-facing tasks to strong models based on content analysis.

---

### Phase 3: Budget, Fallback, and Retry

**Goal:** Cost control and reliability through automatic fallbacks.

**Tasks:**

1. **Budget manager**
   - Per-session, per-day, and per-month budget limits (from `pinyx.json`)
   - Soft warning at 80%, hard block at 100%
   - Budget state persisted in SQLite (`~/.pinyx/state.db`)
   - Budget headers in responses: `X-Pinyx-Budget-Remaining`, `X-Pinyx-Budget-Percent`

2. **Fallback chain**
   - Configurable fallback chains per error type
   - Provider error → try next provider in chain
   - Rate limited → retry same provider, then switch
   - Automatic provider switching on repeated failures

3. **Retry with backoff**
   - Exponential backoff on transient errors (529, 429, 5xx)
   - Configurable max retries per provider
   - Abort signal propagation from Pi (if Pi disconnects mid-request)

4. **Escalation logic**
   - If a cheap model fails, escalate to next tier
   - Track failure history per model (in SQLite) to avoid repeated failures
   - Auto-degrade: if a provider is down, route to backup

5. **Usage API endpoints**
   - `GET /usage` — current usage stats (today, this month)
   - `GET /usage/history?period=day|week|month` — historical breakdown by provider/model/intent
   - `GET /budget` — current budget state with remaining amounts

**Deliverable:** PiNyx reliably handles provider failures and stays within configured budget limits.

---

### Phase 4: Risk Flagging + Permission Hooks

**Goal:** Flag risky actions before they reach providers, integrate with permission system.

**Tasks:**

1. **Risk classifier**
   - Analyze tool calls in request context for risk level
   - Categories: `none`, `low`, `medium`, `high`, `critical`
   - Triggers for high risk: `rm`, `sudo`, `DROP TABLE`, deploy commands, file deletions
   - Triggers for critical: destructive operations combined with production context

2. **Risk hooks**
   - Pre-request hook: inspect and flag risky requests (log warning, add header)
   - Post-response hook: flag responses that suggest risky actions
   - Does NOT block requests (that's the Permission System's job) — only classifies and flags

3. **Webhook support**
   - Optional webhook URL in config for external approval systems
   - `POST` to webhook with risk assessment, wait for approval or auto-timeout
   - Configurable auto-approve timeout

**Deliverable:** Risky operations are flagged in logs and can trigger external approval workflows.

---

### Phase 5: Dashboard + Observability

**Goal:** Bun/TypeScript dashboard for monitoring and control.

**Tasks:**

1. **Dashboard app (Bun + Solid.js)**
   - Real-time request stream (WebSocket from PiNyx)
   - Cost breakdown by provider/model/intent
   - Budget status and projections
   - Model performance comparison (latency, success rate, token usage)
   - Rule editor (visual rule builder)
   - Config editor (edit `pinyx.json` from UI)

2. **WebSocket event stream**
   - PiNyx broadcasts events via WebSocket on `/ws`
   - Events: `request_received`, `classified`, `model_selected`, `provider_called`, `response_streamed`, `error`, `budget_warning`

3. **OpenTelemetry export (optional)**
   - Export traces/metrics to OTEL-compatible backends
   - Per-request tracing: classification → rule evaluation → provider call → response

**Deliverable:** Web UI at `http://localhost:7332` for monitoring all Pi model usage through PiNyx.

## Key Design Decisions

1. **No auth between Pi and PiNyx** — PiNyx binds to `127.0.0.1` only. No token, no API key needed for localhost communication. Security is via network binding.

2. **API keys centralized in PiNyx** — `pinyx.json` holds all real provider keys. Pi only needs the Pi extension loaded (no key configuration in Pi at all). PiNyx resolves env var names or literal values for keys.

3. **JSON config format** — Consistent with Pi/JS ecosystem. No extra Rust deps beyond `serde_json`.

4. **Heuristic classifier first** — Keyword-based pattern matching in Phase 2. Zero model dependencies. Can upgrade to local model classifier later.

5. **Pi extension in Phase 1** — Dynamic model discovery from PiNyx on startup. `/login` → "PiNyx (local)" UX from day one. No manual `models.json` editing.

6. **Rust core (Axum)** — High-performance proxy, low overhead, safe concurrency. Axum has excellent async SSE streaming support for proxying.

7. **SQLite for state** — Lightweight, embedded, no external DB. Budget tracking, request logs, failure history.

8. **Dual API compatibility** — Both OpenAI (`/v1/chat/completions`) and Anthropic (`/anthropic/v1/messages`) endpoints. Any provider Pi supports can be proxied through PiNyx.

9. **Model ID format: `provider/model-id`** — PiNyx exposes models as `anthropic/claude-sonnet-4`, `openai/gpt-4o`, etc. The Pi extension maps these directly. PiNyx parses the prefix to route to the correct provider adapter.

## CLI Interface

```bash
# Start gateway (default: reads ~/.pinyx/pinyx.json)
pinyx

# With custom config
pinyx --config ./my-pinyx.json

# Custom port (overrides config)
pinyx --port 8080

# Verbose logging
pinyx --verbose

# Check status
pinyx status          # queries GET /health on running instance

# Validate config
pinyx check           # validates pinyx.json without starting
```

## Future Considerations (not in scope yet)

- **Local model classifier** — Replace/augment heuristic classifier with Ollama or ONNX Runtime for higher accuracy
- **Multi-user** — If PiNyx runs on a network host (not just localhost), add token auth
- **MCP bridge** — Some future version could expose PiNyx as an MCP server
- **Cloud relay** — PiNyx as a hosted service for teams (keys stored server-side)
- **Prompt caching** — PiNyx could cache identical prompts across sessions
- **Model performance tracking** — Automatic tier adjustments based on observed latency/success rates
